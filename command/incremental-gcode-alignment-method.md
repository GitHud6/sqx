# 基于真实文件的增量式 G-code 对齐方法

## 方法背景

当前项目不是从零设计一套通用 CNC 控制器，而是把 `ray2-main` 中 RayCube 所需的运动和激光业务
逐步迁移到纯 ESP-IDF 架构。

`ray2-main` 的命令能力来自更早的 `ray2-old`，而 `ray2-old` 又继承了 Grbl_Esp32 的完整 G-code
体系。这个继承链带来了一个事实：参考工程能够识别的命令很多，但并不代表 RayCube、LightBurn 灰度
雕刻和当前硬件都需要这些命令。

因此，本项目不以“复制参考工程的全部 G-code 枚举”为完成标准，而以真实目标文件和实际硬件行为为
证据，逐步建立 RayCube 的最小业务子集。

## 核心思想

```text
真实 G-code 文件
    -> SD 作业执行
    -> 遇到未支持命令
    -> 日志记录完整证据
    -> 判断命令业务含义
    -> 选择实现、兼容接收或继续拒绝
    -> 实机验证
    -> 再处理下一条
```

这个方法的重点不是“尽快让文件返回 completed”，而是保证每一个新增命令都有明确的语义依据。

### 为什么不直接移植完整 G-code 解析器

完整 Grbl 解析器包含很多 RayCube 当前不需要的能力：

- 三轴或多轴运动。
- G2/G3 弧线。
- 回零、预置点和坐标系持久化。
- 探测和刀具长度补偿。
- 冷却液、刀具更换和用户 I/O。
- 暂停、覆盖和完整程序控制。

直接复制这些能力会带来三个风险：

1. 引入当前硬件没有对应行为的命令。
2. 让坐标系、激光状态和 Planner 之间出现未经验证的耦合。
3. 让“文件能跑完”掩盖实际运动或激光语义错误。

增量式方法可以将每次变更限制在一个可解释的业务问题内。

## 命令判断原则

遇到一条未支持命令时，不能只根据命令名称决定是否忽略，必须回答以下问题：

1. 该命令是否改变 XY 目标坐标？
2. 该命令是否改变单位、距离模式、进给模式或坐标系？
3. 该命令是否改变激光开关、功率或功率与运动的绑定关系？
4. 该命令是否改变程序生命周期，例如暂停、结束或等待？
5. RayCube 是否存在能够执行该命令的硬件或业务对象？
6. 忽略该命令后，发送端对设备状态的理解是否仍然成立？

根据答案，将命令归入以下三类。

### A 类：必须实现真实语义

命令会影响运动、激光、安全或作业生命周期，不能用空操作替代。

示例：

```text
G0 G1
G20 G21
G90 G91
G94
X Y F S
M3 M4 M5
M2 M30
```

### B 类：可以受约束兼容

命令在当前硬件上没有复杂动作，但必须明确记录状态或限制条件后才能接受。

示例：

```text
G17   固定使用 XY 平面
G40   固定关闭刀具半径补偿
G54   固定使用默认工作坐标系
M8/M9 当前没有冷却硬件时作为明确的无硬件动作状态
```

这类命令不是“未知命令全部忽略”，而是“已确认该命令在当前设备上的安全等价语义”。

### C 类：继续拒绝

命令语义尚未实现，或者当前硬件无法安全执行。

示例：

```text
G2 G3
G38.x
G92
G28 G30
M0 M1
M6
M62-M68
```

继续拒绝是正常状态。拒绝必须可诊断，不能静默吞掉。

## 日志证据要求

### 第一阶段：记录完整 payload

当 SD 作业中的某一行被 `execute_line()` 拒绝时，至少输出：

```text
[SD-GCODE-REJECT] line=4 error=unsupported-command payload="G17 G21 G90 G40 G54"
```

日志必须通过 ESP-IDF 日志系统输出，不得混入 UART 的 LightBurn 协议响应。

UART 仍然只返回原有协议结果：

```text
error:unsupported-command
```

这样既保留了上位机所需的 `ok/error` 语义，也保留了开发阶段的诊断信息。

### 后续诊断增强：记录具体拒绝词

完整 payload 能定位文件行，但一行可能包含多个 G/M 词，因此后续应进一步输出：

```text
[SD-GCODE-REJECT] line=4 word=G17 error=unsupported-command
```

建议在解析器内部增加诊断结果，而不是在 SD 层重新解析 G-code。诊断信息可以包含：

```text
rejected_word
rejected_value
error
line_number
source
```

其中 `source` 至少区分 `uart` 和 `sd`，但不能改变两条输入路径共用的 `execute_line()` 语义。

### 日志内容边界

- 只对失败行输出错误日志。
- 不对每条有效灰度行打印完整内容，避免日志拖慢高频雕刻。
- 日志应限制最大长度，避免异常文件中的超长行造成日志系统压力。
- `$SD/STATUS` 可以保存最后一次失败的行号、词和错误，但不应依赖日志才能判断作业状态。

## 单命令闭环流程

每发现一条新命令，严格执行以下流程：

### 1. 获取证据

记录：

- 文件路径。
- 文件行号。
- 完整 payload。
- 具体被拒绝词。
- 解析器返回错误。
- 作业来源是 SD 还是 UART。

### 2. 查询参考行为

只读取与该命令有关的 `RAY2-main`/Grbl_Esp32 代码，确认：

- 它是模态状态、运动命令、程序控制还是硬件动作。
- 它是否更新 parser state。
- 它是否进入 Planner。
- 它是否改变激光或主轴状态。
- 它是否有错误和安全限制。

### 3. 映射 RayCube 业务

明确写出：

```text
参考命令语义
    -> RayCube 可执行语义
    -> ParserState / MotionRequest / JobState 的落点
```

如果 RayCube 没有对应硬件，必须说明是安全兼容、明确拒绝，还是未来实现，不能直接复制参考代码。

### 4. 实现最小改变

优先只增加：

- 对应的解析分支。
- 必要的临时解析状态。
- 必要的业务状态提交。
- 对应的错误和诊断信息。

不要在同一个步骤中顺便重构 Planner、SD、UART 或激光驱动。

### 5. 做最小验证

验证至少包括：

- 单独发送该命令。
- 将该命令放回真实文件原位置。
- 检查下一条命令是否仍从正确的 ParserState 开始。
- 检查是否产生了不应有的运动或激光输出。
- 检查作业状态和 `ok/error` 数量。

### 6. 决定下一步

只有当前命令完成实机验证后，才能处理真实文件暴露出的下一条未支持命令。

## 实施步骤与验收标准

### 阶段一：增加 SD 拒绝日志

阶段状态：代码已实现，待构建和实机 monitor 验收。

实现内容：

1. 在 `sd_job_service` 的 `command-rejected` 分支输出失败行日志。
2. 日志包含行号、错误文本和完整 payload。
3. 不改变 UART 原有响应。
4. 不对成功的灰度行逐行打印日志。

验收标准：

- `$SD/RUN=/cat.gc` 遇到不支持命令时，monitor 能看到 `SD-GCODE-REJECT`。
- 日志显示正确的 SD 文件行号和完整命令内容。
- UART 仍只收到一次对应的 `error`。
- 作业状态仍为 `faulted`，不会被日志逻辑改变。
- 正常 LightBurn 串口流的 `ok` 数量和响应格式不改变。

结束改动标准：

- 能通过日志直接知道下一条需要分析的完整 G-code 行。

### 命令记录：M9

含义：关闭冷却辅助输出。`RAY2-main` 中的 `M9` 只清空 coolant 状态，不改变 `M3/M4/M5`
主轴/激光状态。RayCube 当前没有冷却硬件，因此此处作为明确的无硬件动作兼容命令接收。

验收标准：

- 单独发送 `M9` 返回一次 `ok`，不生成运动 block；
- `M4 S1000` 后发送 `M9` 不关闭激光；
- `M5 M9` 可在同一行接受，最终关闭激光；
- 重复冷却模态词 `M9 M9` 返回 `error:modal-group-violation`，不能静默吞掉。

### 命令记录：G1 S0

含义：目标文件在作业尾部使用 `G1 S0` 将当前模态激光功率更新为零，但该行没有 XY 位移。
它不是一次零长度运动，不能送入 Planner 形成 `steps=0` 的非法 block。

验收标准：

- `G1 S0` 返回一次 `ok`，且不产生 STEP 脉冲或 Planner block；
- 后续带 X/Y 的 `G1` 继承 `S=0`；
- 裸 `G1` 仍返回 `error:no-axis-words`；
- 真实 SD 文件不再在第 1913 行因 `G1 S0` 停止，而是继续暴露下一条未对齐命令。

### 命令记录：M2

含义：程序正常结束。它不是故障，也不能立即 reset Planner；必须保留之前已经接受的运动顺序，
在末尾提交激光关闭 block 后停止 SD 继续读行，等待 Planner 排空再将作业标记为 `completed`。

验收标准：

- 单独发送 `M2` 返回 `ok`，并按 Planner 顺序关闭激光；
- SD 文件遇到 `M2` 后不再读取其后的内容；
- `$SD/STATUS` 最终显示 `job=completed`、`fault=none`、`error=ok`；
- 已排队的运动完整结束，位置不被 reset 或 invalidated。

实机验收记录：目标灰度文件在第 1918 行遇到 `M2` 后不再报 `unsupported-command`，并可完整
雕刻结束。`M2` 被识别为正常作业结束，不再将 SD 作业置为 `faulted`。

### 命令记录：G00（已实现）

含义：设置快速移动模式，相当于 `G0`。当前这一行没有 X/Y 轴词，因此它不是一次快速移动，
只更新 `ParserState.motion_mode`。

实现边界：

- `G00 X... Y...` 必须继续生成 Rapid `MotionRequest`。
- 单独的 `G00` 或与其他模态同一行的 `G00` 不生成空运动 block。
- 不能为了通过文件头而放宽 `G00` 的坐标和幅面检查。

验收标准：

- `G00 G21` 返回一次 `ok`，不产生 Planner block。
- `G00 X1` 生成 Rapid 运动。
- `G00` 后续的无显式运动模态行仍使用 Rapid 模式。

### 命令记录：G17（已实现）

含义：选择 XY 平面。`RAY2-main` 将 `G17/G18/G19` 放在平面选择模态组，`G17` 是默认 XY 平面。

实现边界：

- `G17` 只更新平面状态，不产生运动。
- RayCube 当前只允许 XY 平面。
- `G18/G19` 在没有对应运动语义前继续明确拒绝。

验收标准：

- `G17` 与 `G21/G90` 同行时返回一次 `ok`。
- 不生成 Planner block。
- 后续 `G1 X/Y` 运动结果与未加入 `G17` 时一致。
- `G18`、`G19` 不会被误当成 XY 平面接受。

### 命令记录：G40（已实现）

含义：关闭刀具半径补偿。`RAY2-main` 明确将刀补保持关闭，支持 `G40` 主要是为了兼容程序头。

实现边界：

- `G40` 只更新“刀补关闭”状态或记录已确认的固定状态。
- 不增加刀具半径计算。
- `G41/G42` 仍然拒绝。

验收标准：

- `G40` 返回一次 `ok`，不产生运动。
- 加入 `G40` 后，后续 XY 目标和步数不变。
- `G41/G42` 返回明确错误。

### 命令记录：G21（已实现）

含义：选择毫米单位。当前 `ray2-idf` 已实现该命令，但需要验证它与同一行中的多个模态词一起出现时，
不会因其他命令失败而提前提交状态。

验收标准：

- `G00 G17 G40 G21` 在其他命令已实现后只更新模态，不产生运动。
- `G21 G1 X1` 的目标为 `1 mm`。
- 解析失败时 `G21` 不会单独提交，保持整行事务性。

### 命令记录：G54

含义：选择 G54 工作坐标系。它不是无条件 no-op；`RAY2-main` 会读取 G54 的坐标偏移，并使用它解释
后续编程坐标。

当前实现：

- `ParserState` 明确记录当前工作坐标系，默认选择 `G54`。
- 当前 G54 偏移固定为 `(0,0,0)`，等价于机床原点工作坐标系。
- `G54` 只更新模态状态，不生成运动请求。
- 绝对坐标先按 `machine_target = work_target + g54_offset` 转换，再进入现有机床幅面检查。
- 暂不实现 NVS 坐标偏移、`G10`、`G92` 和 `G55-G59`。

实机验收结果：

- `$pos/set=0,0` 后发送 `G54`、`G90`、`G1 X1 F600`，`G54` 本身不产生运动，后续运动到
  `X=1 mm`。
- `$pos/set=129,0` 后，`G1 X130 F600` 成功；`G1 X131 F600` 被
  `motion_submit()` 以幅面越界拒绝。
- 当前只完成固定零偏移 G54，不声明支持通用、可配置或可持久化的工作坐标系。
- 该固定零偏移语义已于坐标位置同步阶段完成实机验证并提交。

后续扩展边界：

- 第一版至少建立一个明确的默认 G54 状态。
- 必须明确 G54 偏移是否固定为零，还是来自 RayCube 的配置。
- 坐标系转换必须发生在幅面检查之前。
- 在偏移模型没有确定前，不允许简单忽略 `G54`。

验收标准：

- `G54` 返回一次 `ok`，不产生运动。
- G54 默认偏移为零时，后续 `G1 X/Y` 与当前结果一致。
- 第一版未提供非零偏移配置入口；非零偏移的目标转换列入后续扩展验收。
- 当前坐标路径继续拒绝超出 `[0,130] x [0,110]` 的目标。

## 后续命令追加规则

每次从日志发现新的未实现命令时，在“当前待处理命令队列”末尾追加一条命令记录，不提前建立新的
远期阶段。每条记录必须包含：

```text
发现文件和行号
完整 payload
具体命令
RAY2-main 参考语义
RayCube 处理方向
是否产生运动/激光/状态变化
实现边界
单命令验收标准
原文件位置验收标准
最终处理结果
```

处理一个命令的固定流程：

1. 从 IDF monitor 日志确认真实输入。
2. 查看 `RAY2-main` 对该命令的解析和执行语义。
3. 判断是必须实现、受约束兼容还是继续拒绝。
4. 只实现当前命令所需的最小状态和业务行为。
5. 先做单命令测试，再放回真实文件原位置测试。
6. 实机验证通过后填写处理结果。
7. 开始下一个命令前提交当前改动。

## 与提交节奏的关系

强制规则：每实机验证通过一个 G-code 命令，就必须立即进行一次本地 Git 提交，
再开始处理下一个命令。不能把多个已经验证的命令合并到一次提交中。

每完成一条命令的实现并通过对应实机验收，就完成一个独立的小步骤。执行顺序为：

1. 更新本文件中的命令分类、实现位置和验收记录。
2. 完成该步骤的实机验证。
3. 立即进行本地 Git 提交。
4. 提交内容只包含当前命令及其必要测试、文档改动。
5. 提交完成后才能开始处理下一条命令。

这样可以保证每个 G-code 能力都能单独回溯，不会把多个未经验证的命令混成一次大改动。

## 方法的边界

这个方法适合当前“真实文件驱动的增量迁移”，但不能替代最终的系统性测试。完成一批命令后，仍然
需要定期做一次完整回归，防止模态状态之间产生组合问题，例如：

```text
G91 + G20 + G1 + F 组合
G54 + G90 + 幅面检查组合
M4 + S + 短行 Planner 排队组合
M2/M30 + M5 + SD EOF 排空组合
```

因此最终策略是：

```text
短期：遇到一个处理一个，以真实日志为入口。
中期：把已确认命令整理成 RayCube 最小 G-code 规范。
长期：对最小规范做组合测试，而不是继续追求完整 Grbl 命令数量。
```
