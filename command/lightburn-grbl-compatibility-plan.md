# LightBurn Grbl 兼容性对齐计划

## 目标分析

当前工程已经能执行 RayCube 灰度文件的主要 G-code 路径：`G0/G1`、`G17`、`G20/G21`、
`G40`、`G54`、`G90/G91`、`M2`、`M3/M4/M5`、`M9`、`X/Y/F/S`。词法层也支持注释、
大小写和无空格词，例如 `G1X0.05S103.9`。

但 LightBurn 与设备连接不是仅发送普通 G-code。它还依赖无需行结束符的实时字符、Grbl 格式
状态报告、`$` 系统命令、点动命令以及矢量作业中的圆弧。阶段一已将 `?`、`!`、`~`、`0x18`
从普通行接收流分离；但标准状态报告和这些字符的控制语义尚未实现，因此还不能视为完整的
LightBurn Grbl 设备。

本计划的首要对照项目是 `D:\ray2-old`：

- 普通 G-code：`components/Grbl_Esp32_Source/Grbl_Esp32/src/GCode.cpp`。
- `$` 系统命令：`ProcessSettings.cpp`。
- 实时字符筛选：`Serial.cpp`。
- 状态机与状态报告：`Protocol.cpp`、`Report.cpp`。

不以通用 Grbl 文档自行增加命令。每一个命令先确认 `ray2-old` 的实际解析、状态转换和响应，
再判断 RayCube 是否具备对应硬件和安全语义。

## 当前支持与缺口

| 类别 | 当前已支持 | 当前缺口 | 所属模块 |
| --- | --- | --- | --- |
| 普通直线 G-code | G0/G1、G17、G20/G21、G40、G54、G90/G91、M2、M3/M4/M5、M9 | G2/G3、M30、M0/M1、G4 等 | `command`，部分依赖 `motion/planner` |
| 实时字符 | `?`、`!`、`~`、`0x18` 的单字节接收分流与计数 | `?` 标准状态报告、Hold、Resume、Reset 控制语义 | `protocol` / UART 接收路径 |
| Grbl 主机报告 | 自定义 `$POS/STATUS` | 标准 `<Idle|...>` 状态、`[GC:...]`、`[G54:...]`、`[VER:...]` | `protocol` / report 接口 |
| `$` 系统命令 | `$H`、`$POS/*`、`$SD/*` | `$I`、`$$`、`$G`、`$#`、`$X`、`$J=` | `protocol` / system-command dispatcher |
| 工作坐标 | 固定零偏移 G54 | G10、G92、G55..G59、持久化 | 后续坐标系统模块 |

## 设计边界

```text
UART RX 字节
  -> realtime filter: ?, !, ~, 0x18
  -> LineAssembler: 普通 G-code / $ 系统命令
  -> protocol system-command dispatcher: $I / $$ / $G / $# / $X / $J=
  -> command::execute_line(): 仅普通 G-code 语义
  -> motion / planner / stepper
```

- `command_executor` 只解析并提交完整普通 G-code 行，不处理无行结束符的实时字符。
- `$` 命令由 `protocol` 的系统命令分发器处理；其中 `$J=` 可复用 G-code 解析，但不应让
  `execute_line()` 自己识别所有系统命令。
- `planner` 仍拥有 Hold、Resume、Reset 与执行生命周期；协议层只翻译主机命令。
- 标准状态报告由协议/报告层组合 `planner`、`stepper`、`homing` 的只读快照，不直接修改状态。
- 对没有硬件的冷却、探针、刀具等命令，必须根据 `ray2-old` 和 RayCube 实际能力明确选择
  安全接受、明确拒绝或延后实现，不能伪造执行成功。

## 实现步骤与验收标准

### 阶段一：实时字符与普通行分流

阶段状态：已完成，已通过实机验收。

实现内容：

1. 在 `protocol_task` 中、`LineAssembler` 之前识别 `?`、`!`、`~` 和 `0x18`，不让它们进入普通行缓冲。
2. 定义仅表示接收结果的 `RealtimeCommand` 接口和只读接收统计；该接口不调用 planner、laser、
   homing 或 reset。
3. 普通字节继续按原顺序送入 `LineAssembler`；实时字节被消费后，不得改变其前后普通字节的内容、
   换行边界或错误处理。
4. 将实时接收统计附加到已有工程诊断，供本阶段实机验证；不在本阶段输出标准 Grbl 状态行。
5. Hold、Resume、Reset 的实际业务和 `?` 的标准状态报告留给后续独立阶段实现。

验收标准：

- `?`、`!`、`~`、`0x18` 没有 `\r`/`\n` 时被识别并计数，且不会生成 `error:expected-command-letter`。
- 将实时字节插入 `G1 X1 F600` 的接收流时，普通行仍按原样执行或在原有校验规则下拒绝，不能被截断、
  拼接或改变词法含义。
- 连续灰度流中发送 `?` 不进入行缓冲，不产生 overflow，不改变后续 payload 的执行顺序。
- 本阶段不改变 Hold、Resume、Reset、激光或机床位置；诊断只证明分流，不声明控制功能已完成。

结束改动标准：

- 实时字符与完整行命令的接收路径已物理隔离。
- `RealtimeCommand` 已成为后续控制和报告阶段的唯一接收接口。
- 实机诊断已证明四类实时字节不会泄漏进 `command::execute_line()`。

实机验收记录：

- 无 `\r`/`\n` 发送 `?`、`!`、`~` 和原始字节 `0x18` 后，`$POS/STATUS` 中对应的
  `realtime` 计数均按预期变化。
- 将 `?` 插入普通运动行后，运动仍按剥离该字节后的 payload 执行。
- `0x18` 必须由串口工具按原始控制字节发送；发送文本 `0x18` 会作为普通行进入 G-code
  解析器并返回 `error:expected-command-letter`，不属于实时分流失败。
- 扩展后的 `$POS/STATUS` 诊断缓冲区已移出 `protocol` 任务栈，避免长诊断输出导致栈溢出。

### 阶段二：标准 Grbl 状态、身份和模态报告

实现内容：

1. 为 `?` 输出标准 Grbl 风格状态，例如 `<Idle|MPos:...|WPos:...|FS:...>`；字段精度和
   状态名称以 `ray2-old` 实测输出为准。
2. 实现 `$I`，报告稳定的固件标识与版本信息。
3. 实现 `$G`，从 `ParserState` 输出当前 G-code 模态。
4. 实现 `$#`，输出当前 G54/WCO；当前只有零偏移时也要用标准报告格式明确表达。
5. 保留 `$POS/STATUS` 作为工程诊断命令，不把其内部诊断字段混入标准 `?` 输出。

验收标准：

- LightBurn 连接后能识别设备身份，并持续解析 `?` 的状态行。
- `$G` 输出与已执行的 G20/G21、G90/G91、G0/G1、M3/M4/M5 模态一致。
- `$#` 与当前 G54 坐标转换一致；执行 `$H` 或显式位置确认后 MPos/WPos 关系正确。
- 作业运行中状态报告不阻塞 planner，不造成 segment underflow 或 watchdog。

结束改动标准：

- 标准主机报告与工程诊断报告职责分离。
- 所有报告都来自只读快照，没有报告路径修改运动或解析器状态。

### 阶段三：基础 `$` 系统命令与 LightBurn 点动

实现内容：

1. 实现 `$$` 的只读兼容报告，优先覆盖 LightBurn 读取的机型能力：最大 S 值、激光模式、
   轴步距、最大速度、加速度、行程、junction deviation 等。是否允许写入设置另行决定。
2. 实现 `$X`：仅在 Alarm 状态下按 `ray2-old` 的前置条件解除锁定；不能借此伪造可信坐标。
3. 实现 `$J=G91 X... Y... F...` 的受控点动路径，使用独立 Jog 状态并限制幅面、速度、
   Busy 与 Alarm 行为。
4. 明确 `$H`、`$X`、`$J=` 与 SD 作业、planner Busy、位置可信度之间的互斥规则。
5. 暂不实现设置持久化、`$N` 启动行与 `$RST=*`；这些命令先明确返回行为。

验收标准：

- LightBurn 能读取 `$$` 并将最大功率识别为 `S1000`，不把 RayCube 错当作非激光设备。
- Alarm 时普通运动被锁定；`$X` 仅在允许条件下退出 Alarm，位置可信度不被错误提升。
- LightBurn 的方向键/点动命令生成的 `$J=` 能在幅面内移动，Busy、Hold、Home 或 Alarm 时被安全拒绝。
- SD 灰度作业运行时，点动和归零命令不能抢占或污染现有作业。

结束改动标准：

- 系统命令不再由 `command_executor` 统一拒绝。
- 点动的生命周期与普通 G-code、归零和作业状态边界明确。

### 阶段四：普通 G-code 的作业控制补齐

实现内容：

1. 参考 `ray2-old` 实现 `M30`，并对齐 `M2/M30` 的程序结束、激光关闭与必要模态复位语义。
2. 评估并实现 `M0/M1` 的暂停语义，接入实时 Resume，而不是把它误作普通激光关闭。
3. 评估 `G4 P...` 是否被 LightBurn/Ray2 作业真实使用；若需要，按可中断的 dwell 语义实现。
4. 继续保持 `M9` 为无冷却硬件下的安全兼容命令；M7/M8 只在确认 RayCube 有对应硬件后处理。
5. 对真实文件新出现的命令，先记录原始 payload、文件行号和 `ray2-old` 行为，再按本计划增量补齐。

验收标准：

- `M2`、`M30` 后无待执行运动和残留激光输出，后续新作业从一致的模态开始。
- `M0/M1` 不丢失已入队的运动顺序，Resume 后安全继续或按 `ray2-old` 行为结束。
- 已实现的兼容命令不会创建零步 block、污染 planned position 或错误回复 `ok`。

结束改动标准：

- 程序控制命令的效果与运动队列、激光安全和 ParserState 事务一致。

### 阶段五：圆弧 G2/G3 与工作坐标扩展评估

实现内容：

1. 收集 LightBurn 矢量作业的真实 G2/G3 payload，确认使用 `I/J`、`R`、平面和单位形式。
2. 以 `ray2-old` 的圆弧语义为参考，设计圆弧离散化为连续 G1/PlannerBlock 序列的接口。
3. 圆弧实现必须通过现有 motion/planner/segment 路径，不能在 command 层直接发 STEP。
4. 仅在实际需求出现后评估 G10、G92、G55..G59；当前固定 G54 不因“通用 Grbl 完整性”而提前扩展。

验收标准：

- 圆弧端点、方向、半径/中心校验、幅面限制和最终位置与 `ray2-old` 一致。
- 圆弧离散段保持 junction 连续性、无 segment underflow、无激光功率提前泄漏。
- 不支持的坐标系或圆弧形式返回明确错误，不静默退化为错误直线。

结束改动标准：

- 已由真实 LightBurn 矢量作业证明确有需求并完成对应形式；否则保留为未实施边界。

## 不纳入本计划

- Wi-Fi、WebUI、Bluetooth、Telnet 等传输层。
- 未确认存在的刀具、探针、冷却、自动换刀或多轴硬件业务。
- 为模拟通用 Grbl 而提前实现所有 `$` 设置持久化。
- 通过放宽错误处理来让未知 G-code 文件“看起来能跑”。

## 最终完成标准

1. LightBurn 可以识别设备、读取能力、显示实时状态、归零、点动并安全停止/恢复。
2. 普通灰度和矢量作业使用的实际 G-code 均经 `ray2-old` 对照后支持或明确拒绝。
3. 实时字符、系统命令、普通 G-code 和工程诊断的职责边界清晰。
4. 任何 Abort、Hold、Reset、Alarm、Home 或作业结束都不会留下运动、激光或不可信位置的隐患。
5. 每个阶段完成实机验收后，按项目规则先提交本阶段改动，再开始下一阶段。
