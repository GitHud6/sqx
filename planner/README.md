# 运动规划模块

`planner` 将已量化的运动请求组织为有界的 `PlannerBlock` 队列，并在可变的前瞻窗口内求解相邻路径的速度边界。它向 `stepper` 发布冻结后的 block，而不参与脉冲生成。

## 职责

- 维护 block 队列及其 `Lookahead`、`Frozen`、`Executing` 生命周期。
- 根据路径长度、轴约束和转角连续性计算 nominal、entry 与 exit 速度边界。
- 对可变窗口执行正反向前瞻；已冻结或正在执行的前缀不可被后续输入改写。
- 接收执行完成、取消、故障和排空事件，回收 block 并向上游反馈执行状态。

## 边界

- 不解析 G-code，不读取通信输入，也不决定任务生命周期。
- 不生成 profile、segment、DDA 或外设时序。
- 不直接操作激光、SD、Timer 或 RMT；这些动作分别由 `service`、`stepper` 与 `driver` 负责。
- 回调运行在调用方任务中，必须快速返回且不得重入 planner API。

## 修改步骤

1. 修改速度数学前，先明确影响范围是 block 构建、junction 约束还是前瞻传播。
2. 保证冻结前缀不被改写，队列回收只由执行事件驱动。
3. 变更队列容量或 block 字段时，同步检查 `motion` 的原子批量提交和 `stepper` 的消费路径。
4. 保持诊断在任务上下文，禁止把格式化或日志引入实时执行路径。

## 验收标准

- 连续路径的相邻 block 速度边界一致，不出现不连续跳变。
- 队列满、重置、排空和执行故障均不会遗留不可回收 block。
- 已发布的执行前缀不受后续命令影响。
- planner 不依赖具体输入介质和脉冲外设。
